## 一、原设计思路回顾(概念文档 + 开发计划)

### 1.1 概念文档 §6 知识库设计的核心思路

产品概念文档把「知识库」定位为系统**「越用越好」核心卖点的底座**,并明确采用**双引擎设计**:

| 引擎 | 存储 | 匹配方式 | 为什么用这个引擎 |
|------|------|---------|-----------------|
| RAG 术语库 | ChromaDB + bge-m3 | 语义检索 | 术语跨语言无字符串相似度(如 `container orchestration` vs `容器编排`),必须语义 |
| 翻译记忆 TM | SQLite + RapidFuzz | 字符串模糊匹配 | ICT 文本高度模板化、重复率高,字符串匹配精准且零成本 |
| 用户偏好 | SQLite | 键值存取 | 记录风格/术语偏好 |

**三级查证(§6.2)**:译前术语提取对每个候选术语按「**RAG 命中 → Web 搜索 → LLM 生成**」逐级降级查证,并把结果合并进**项目术语表**(当前项目的工作记忆),主译直接对照术语表强制使用,不再重复查 RAG。

**领域标签消歧(§6.2)**:策略制定先识别 ICT 子领域 → 术语提取携带领域标签 → RAG 按领域过滤,支持同词多译(如 `container`:kubernetes 域→"容器"、docker 域→"容器镜像")。

**TM 译前参考 + 译后写入(§6.3)**:译前一次性全文模糊搜索注入主译 prompt 作参考;译后质检 ≥8.5 的句对经句级对齐写入。

**持续进化机制(§6.4)**:术语确认 → `write_rag` 入库;高分句对 → `write_tm`;用户干预 → `save_prefs`。第 20 次使用时 RAG 命中率从首次约 20% 升至 85% 以上,这是演示的核心叙事。

### 1.3 数据契约(contracts.py,与开发计划 §3 完全一致)

```python
@dataclass
class TermEntry:
    term: str
    translation: str
    domain: str = ""
    confidence: str = "medium"      # "high" | "medium" | "low"
    action: str = "translate"       # "translate" | "notranslate"
    source: str = ""                # "RAG命中" | "Web搜索" | "LLM生成" | "用户确认" | "种子数据"

@dataclass
class TMEntry:
    source_seg: str
    target_seg: str
    quality_score: float = 0.0
    similarity: float = 0.0
```

**本报告所有解决方案都以「不改变 6 接口签名、不新增 TermEntry/TMEntry 字段」为前提**,新添加的模块会明确标注【新增】。

## 三、第一次测试发现的问题与解决方案

### 3.1 问题清单(按严重度排序)

| # | 问题 | 证据 | 严重度 |
|---|------|------|--------|
| **P1** | **同域近义误报 4/16** | GAN→GenAI(0.79)、Transfer Learning→Supervised Learning(0.73)、Signature Verification→Digital Signature(0.76)、Handwritten Signature→Digital Signature(0.73),相似度远超 0.70 | 高 —— 库外术语会被当高置信注入,**Web 兜底救不了**(错误已被判定为命中) |
| **P2** | **召回率 100% 是"虚高"** | 29 条命中里 22 条是全称送分题(相似度 1.00);纯语义路径 0.70 下只有 76%(22/29),其余靠别名层兜底;无别名层整体仅 86.2% | 中 —— 单看 100% 会高估语义检索能力 |
| **P3** | **覆盖缺口 21 个库外术语** | A 类 16 个已测(GAN、VGG-16、Transfer Learning、Signature Verification 等)+ B 类补充 5 个(CRM、ERP、AWS、GCP、HIPAA) | 中 —— 真实覆盖缺口,也是误报的来源 |
| **P4** | **测试集是"反向召回"** | 测试查询从词库术语出发反查文章,命中全是"文章恰好出现的形式";未模拟 LLM 术语提取常见的**同义改写**与**中文反向** | 低-中 —— 测试代表性不足 |

### 3.2 解决方案(逐项标注接口符合性 / 是否新增)

#### 方案 A:扩库 —— 主修 P1 误报 + P3 覆盖缺口(无新增接口,**已落地 2026-08-10 批次1**)

**思路**:4 个误报术语本质是**「文章出现但词库没有」**,RAG 才会错误命中同主题的近义词。把正确术语补入词库后,查询会以约 **1.00 相似度命中自己**(测试里所有全称直查均为 1.00),近义误报自动消失:

```
扩库前:查询 "Signature Verification" → 库内只有 Digital Signature → top1=0.76 误报
扩库后:查询 "Signature Verification" → 库内新增 "Signature Verification" → top1=1.00 正确
        Digital Signature 跌到次位(0.76),不再被错误注入
```

同时缩写别名层自动生效:若扩库项带括注(如 `Generative Adversarial Network (GAN)`),`GAN` 裸缩写也会走别名层确定性命中,双保险。

**推荐优先级**:

| 批次 | 术语 | 理由 |
|------|------|------|
| **1(直接消误报)** | GAN、Transfer Learning、Signature Verification、Handwritten Signature | 消除全部 4/16 误报 |
| **2(B 类高频)** | CRM、ERP、AWS、GCP、HIPAA | 企业软件/云/合规,出现即高频 |
| **3(A 类深度学习)** | VGG-16、Max-Pooling、Softmax、ReLU、Feature Extraction、Fraud Detection | AI/ML 文章常客 |
| **4(通用)** | Kubernetes、Hadoop、Apache Spark、E-commerce、GDPR、V2X | 通用 ICT 高频 |

**落地方式(全用现有接口)**:整理成 `ICT_Terms_ext.xlsx` / CSV,跑
```
.\venv\Scripts\python.exe knowledge_base/import_glossary.py ICT_Terms_ext.csv --source "真实文档测试扩库"
```
(增量导入自动 upsert,不重建内置库);或由 A 端在译后确认时逐条调 `write_rag`。

#### 方案 B:近义消歧表 —— 兜底 P1 的"改写查询"漏网之鱼(【新增】模块,接口不变,**已落地 2026-08-10**)

扩库能消掉"查询 = 术语本身"的误报,但 LLM 术语提取可能输出**同义改写**(如 `"signature matching system"`),改写后与库内近义词的相似度排序仍可能误配。加一道确定性护栏:

- **新模块**:`knowledge_base/rag_disambiguation.py`(SQLite 表 `disambiguation_rules`,可并入 `rag_aliases.db`)
- **规则形如**:`(query_pattern, blocked_term, reason)`,例:`("signature", "Digital Signature", "签名类:Signature Verification/Handwritten 未命中时勿回退数字签名")`
- **逻辑**:`search_rag` 内部,在语义检索 top_k 中若 query 命中规则、且 top-1 恰为被排除术语 → 抑制该候选;剩余候选仍 ≥ 阈值则返回,否则返回 `[]` → 调用方**按既有三级查证转 Web 搜索**(正确行为,而非静默给错译)
- **符合性**:`search_rag(query, domain, user_id, top_k)` 签名不变;不新增 `TermEntry` 字段;规则表是模块内部工具(可加 `add_rule`/`list_rules` 辅助函数,但**不对外导出**,6 接口保持冻结)
- **定位**:P1 增强。扩库已解决 4/16,消歧表防的是未来文档里的改写变体。

#### 方案 C:学习层回写闭环 —— 修 P1 的结构性根因(无新增接口,需 A 端配合,**代码就绪 2026-08-10**)详见优化日志-04

误报的深层原因是**词库是静态的**。概念文档 §6.4 已设计学习层:**译后用户确认的术语 → `write_rag` 自动入库**。闭环后,首次遇到 `Signature Verification` 时的误报,经用户确认正确译法后立即入库,下一次就确定性命中——这正是演示"越用越好"叙事的数据来源。

- **接口**:`write_rag(entries: list[TermEntry], user_id)` 已存在,`source="用户确认"`,按 (user_id, term) upsert,重复确认自动覆盖
- **落地**:属 A 端(orchestrator 译后流程)集成,本模块无需新增代码

#### 方案 D:测试集增强 —— 修 P4 代表性不足(测试侧,零业务代码改动,**已落地 2026-08-10**)详见优化日志-06

第一次测试查询全部来自文章表面形式,是"逆向召回"。补三类查询让指标更贴近真实管线:

| 类型 | 示例 | 考验点 |
|------|------|--------|
| 同义改写 | `"signature matching"` → Signature Verification | 语义路径真实能力 |
| 裸缩写(无括注) | `"DL"` → Deep Learning | 别名层 + 无括注缩写 |
| 中文反向 | `"数字签名"` → Digital Signature | 中文源文支持(若产品支持) |

**同时调整指标口径**:把召回率拆成「别名命中」与「语义命中」两条分别报告,避免 100% 掩盖语义路径只有 76% 的事实;阈值敏感性分析保留(0.70 是召回/误报平衡点,**不建议调阈值**——提到 0.80 虽把误报压到 0,但语义召回从 22 掉到 15)。

## 四、结论

1. **RAG 搭建已超出原设计文档**:"缩写别名层"、"官方 200 条内置库"、"术语表导入器"、"真实文档测试体系" 4 项均为概念文档/开发计划之外的新增能力(详见 §2.2),是第一次测试 100% 召回的实现基础。
2. **第一次测试唯一的实质问题 = 同域近义误报(4/16)**,根因是**覆盖缺口**(21 个库外术语)+ **缺少消歧护栏**;召回虚高、测试集反向是评估口径问题,不是检索缺陷。
3. **主修路径是"扩库"(现有接口,零新代码)**:批次 1 的 4 条术语即可把误报归零,同时收窄覆盖缺口;「近义消歧表」作为改写查询的兜底护栏(P1)。
4. **学习层回写(A 端集成)是根治方案**:让词库从静态变动态,配合演示"越用越好"叙事。
5. **0.70 阈值经两轮测试确认是最优点,不建议调整**;后续以「结构手段(扩库/消歧/别名)+ 评估口径(拆分语义/别名召回)」替代调阈值。
